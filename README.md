# PubMed GraRec Notion — 共通取り込み・OneDrive版

PDF → JSON → PNG → 確認・Notionへの登録を、PDF自動取得・JSONのBatch API・PNG確認後のNotion登録・手動作業・一括取り込みで進めます。完成した一式をまとめて取り込むこともできます。
**手動ルートはAPIキーなしで利用できます。JSONのBatch作成にはOpenAI APIキー、画面からのNotion登録にはNotion接続キーが必要です。自宅と職場のMacは、OneDrive上の同じファイルと進捗記録を使います。**

## 起動

`PubMed-grareko-notion.app` または `PubMedGraRecAuto.command` を開きます。`PubMedGraRec.command` も同じ画面を開きます。

カードと論文一覧の基本構成を維持し、区分は次の6つに変更しました。

- PDF取得待ち
- JSON作成待ち
- PNG作成待ち
- PNG確認・登録待ち
- 登録完了
- 要確認・競合

PDF自動取得と、画面で対象を確認して実行するJSONのBatch送信・回収を利用できます。選択・確認後のNotion登録も利用できます。PNG生成API・定期的なAPI回収・無人でのNotion登録は接続していません。PDF自動取得はPubMedと公開PDF配布元にアクセスし、JSON BatchはOpenAIへ選択したPDFと依頼文を送信します。形式確認、ファイルコピー、依頼文準備、進捗記録はローカルで行います。

## 共通フォルダを設定する

各MacでOneDriveに同じアカウントでサインインし、同じ専用フォルダ `PubMed_GraRec` を同期します。
アプリの「このMacの設定」で、そのMac上の共通フォルダの絶対パスと端末名を指定します。
初回のみ空の専用フォルダを作成します。職場では、先に自宅で作成した `workspace.json` が同期されたフォルダを選んでください。

自宅Macの例:

```text
~/Library/CloudStorage/OneDrive-個人用/PubMed_GraRec
```

端末名の例: `自宅 MacBook Air`、`職場 Mac`。ローカル設定はGit管理外の `output/manual_settings.json` に保存し、他のMacへコピーしません。

既存データがあるMacでは「このMacの旧台帳からファイルをコピー」を1回実行します。旧台帳の最新選択中のPDF・JSON・テーマ別JSON・PNG・依頼文を実ファイルとしてコピーします。共有側に登録済みのPMIDは上書きしません。旧台帳・旧版・元ファイルは元の場所に保持します。

CLIで同じ設定を行う場合:

```sh
.venv/bin/python scripts/setup_manual_workspace.py \
  --root "$HOME/Library/CloudStorage/OneDrive-個人用/PubMed_GraRec" \
  --device-name "自宅 MacBook Air" --copy-legacy
```

職場では初回に `SetupPaperPipeline.command` で環境を準備し、アプリで同じ共有フォルダを選択します。Gitで渡すものはアプリのソース、OneDriveで渡すものは論文ファイルと進捗です。

## 普段の操作

1. アプリを開くと共通フォルダ内に `00_取り込み待ち` と `01_取り込み済み` が作られます。既存のファイルを一括移動する必要はありません。
2. PubMed Abstractの希望PMIDのTXTを `00_取り込み待ち` に保存します。画面からのPMID入力・TXT選択も利用できます。PMIDだけの行、`PMID: 番号`、PubMed URLに対応し、重複は除きます。
3. `PMID_番号.pdf`、Webで作った `PMID_番号.json`、`PMID_番号_テーマID.png`（例: `PMID_40522178_overview.png`）を `00_取り込み待ち` 直下に保存します。論文別フォルダの作成は不要です。任意のメモにはPMIDを記載します。どの端末からでも保存できます。PDFだけ、JSONだけ、完成した一式など、途中の工程から合流できます。JSONの取り込みには保存済み、または同時投入の本文PDFが必要です。
4. Macの画面で **「取り込み・整理」** を押すか、このリポジトリの **`取り込み・整理.command`** をダブルクリックします。アプリを開かずに `.command` だけで整理することもできます。共通の取り込み待ちは、起動や定期確認だけでは整理しません。
5. PDF→JSON→PNGの順に検証し、揃ったファイルから工程を判定します。途中の工程を1つずつ操作する必要はありません。成功した入力だけを `01_取り込み済み/取り込みID/` に移して保管します。元の相対フォルダ構成を保持し、既存の保管ファイルは上書きしません。
6. 原文・JSON・PNGを照合し、画面の「PNG確認・Notion登録」から登録します。手動でアップロードする場合は、論文一覧の「確認・登録の記録」で確認内容・登録先URL・完了チェックを記録します。メモに「作成済み」「登録済み」と書いただけでは完了にしません。
7. 端末を切り替える前に、OneDriveアプリでアップロード・同期の完了を確認します。

画面上部の工程ボタンは該当する論文へ絞り込み、一覧まで移動します。JSON・PNGの依頼文は各論文のコピーボタンで準備します。「登録総数」はPMID単位で数え、取り込み待ちはファイル単位で別表示します。整理結果と、残した入力の理由も表示します。

同じ論文だけなら `00_取り込み待ち` へ直接一式を置くこともできます。JSON内のPMID、`PMID_番号` フォルダ、`PMID_番号_main.png` などのファイル名、PMID付きメモから対応を確認します。同じ場所に複数のPMIDがあり特定できないファイルは残します。複数論文もPMID付きのファイル名で直下に保存できます。PMIDごとのフォルダも引き続き利用できます。メモの自由文をAIで解釈する処理はありません。

同じファイルの再投入は既存として扱い、古い版を再採用しません。新しい候補が複数、PMID不一致、保存・同期直後、不正なファイルなどは入力を残します。古いPDF・JSONと新しい後続成果物の混在も保留します。入力を修正して再度「取り込み・整理」を実行してください。同じMacでアプリと `.command` が同時に動いた場合は、共有フォルダ単位で順番に処理します。別Macとの同期競合は従来どおり履歴に残し、要確認とします。

既存の論文別 `受け渡し/PDF`、`受け渡し/JSON`、`受け渡し/PNG` も利用できます。こちらはアプリ起動時と約30秒ごと、または「保存状況を確認」で確認・記録します。共通取り込み待ちと論文別受け渡しへ、異なる候補を同時に置かないでください。

保存済みの版は変更せず、差し替えたファイルは新しい版として保存します。PDFの差し替えでJSON以降、JSONの差し替えでPNG以降の現行選択と完了状態を解除し、前の版は履歴に保持します。

### Webへ渡すファイルの見分け方

全文JSONは画像1枚の論文でも作る共通工程です。画像の分割はページ数ではなく、独立した疑問・テーマと情報量で判断します。

| 用途 | ファイル名の例 | Webへ渡すもの／完成物 |
| --- | --- | --- |
| PDFから全文JSONを作る依頼 | `PMID_40522178_JSON作成依頼_PDF添付.txt` | このTXT＋本文PDF → `PMID_40522178.json` |
| テーマのPNGを作る依頼 | `PMID_40522178_overview_PNG作成依頼.json` | このJSON1個（依頼文・描画ルール・画像用データを内包）→ `PMID_40522178_overview.png` |
| 全文JSONの完成データ | `PMID_40522178.json` | `00_取り込み待ち` 直下へ保存し「取り込み・整理」 |

一覧の「JSON作成依頼TXTの場所を開く」「PNG作成依頼JSONの場所を開く」で、現在のデータから依頼を準備しFinderで選択表示します。旧記録でも利用でき、元のPDF・JSON・PNGや完了状態は変更しません。依頼文をコピーしてWebへ貼り付ける方法も利用できます。PNG作成依頼JSONは完成データではないため、取り込み待ちに入れると案内を表示して残します。

通常のPNG作成ではPDFの再添付は不要です。JSONの内容を原文と照合・訂正する場合は、PDFとJSONの両方が必要になることがあります。旧 `master.json` や `40522178_master.json` も引き続き取り込めます。ファイル名を変えるだけで形式を変換する必要はありません。

JSONは従来の `hybrid-v1` Master JSON形式です。自由形式のJSONや画像用JSONだけを新しい全文JSONとして取り込むことはできません。依頼文に必要なSchemaが含まれます。構文・対応の検証は医学的正確性の保証ではありません。

JSONの形式と論文・原本との対応は正しくても、テーマへの推奨割り当て漏れや章IDの不整合がある場合は、一覧に **「生成済み・構造確認待ち」** と表示します（上部の「要確認・競合」に集計）。生成されたJSONはDRAFTファイルとして履歴に保持し、理由と該当IDを表示します。修正したMaster JSONを受け渡しのJSONフォルダに保存すると再検証し、合格後にテーマ別PNG作成へ進めます。以前の版が残っていても、構造確認待ちの間は画像依頼文のコピーを止めます。

2026-11-13に生成指示を改善しました。参照する小節・図表を章一覧に登録し、IDの完全一致と全結果・全推奨の割り当てを出力前に確認するよう指示します。ローカルの整合性検証も引き続き行います。

## PDFを自動取得する（段階3）

1. アプリを終了して再起動し、先にPMIDを登録します。希望PMIDのTXTを取り込み待ちに置いた場合は「取り込み・整理」を実行してください。
2. 工程「PDF取得待ち」の **「自動取得」** を押します。論文一覧の **「PDF自動取得」** から1本を選ぶこともできます。
3. 対象をチェックし、**「選択した論文のPDFを取得」** を押します。最大50本を順番に処理し、処理中のPMIDと進行状況を表示します。ボタンを押していない論文を自動取得することはありません。
4. PDFの構造を検証し、先頭ページのタイトルとDOIまたはPMIDを照合します。一致した本文PDFは `papers/PMID_番号/files/内容ハッシュ/PMID_番号.pdf` に保存し、JSON作成待ちへ進めます。Web用のJSON作成依頼文も準備します。OneDriveクラウドへのアップロード完了はOneDriveアプリで確認してください。
5. 取得結果の各論文を開くと、理由・保存したPDF・手動確認先を確認できます。未取得分はPDF取得待ちのままです。再試行する場合は対象を選び直してください。

検索処理は既存の `pubmed-pdf-fetcher` の `PdfFinder` を再利用しています。PMC、Unpaywall、Europe PMC、出版社の公開リンク・PDFメタデータを順番に確認します。別の `pubmed-pdf-fetcher` リポジトリの配置は不要です。`scripts/paper_pipeline/pdf_finder.py` は同リポジトリの `92831f7` から取り込み、PDFを名乗るHTML応答を除外する先頭バイト確認を追加しました。書誌取得には既存の `pubmed.py` を使います。追加の依存ライブラリはありません。

AI APIキーは不要です。Unpaywallは実行環境の `UNPAYWALL_EMAIL` が設定されている場合だけ使い、未設定なら他の検索先へ進みます。NCBIの任意の `NCBI_EMAIL`・`NCBI_API_KEY` も既存の処理に従います。`.env` は読み込みません。OpenAI・Notion APIは呼び出しません。

- 本文と書誌情報の一致を確認できないPDFは「PDF候補・要照合」として同じ共有フォルダへ保管し、PDF取得待ちを維持します。原本を確認し、正しい本文PDFなら `00_取り込み待ち/PMID_番号/` へコピーして「取り込み・整理」で採用してください。構造不正・暗号化・49MiB超のPDFは自動採用しません。
- 取得済みのPDFや後続のJSON・PNGは置き換えません。手動保存したPDFが取り込み待ち・受け渡しにある場合は、先にそちらを整理します。
- 通信中は共有フォルダのロックを保持せず、保存前に記録の版を再確認します。別端末で更新された場合は取得PDFを候補として保管し、既存の記録を上書きしません。
- 認証・CAPTCHA・所属機関ログインが必要な論文は、取得結果の「手動確認先を開く」で標準ブラウザーへ引き継ぎます。
- 処理中はMacのアプリを開いておいてください。中断後は保存済み分を保持し、次回は未取得の論文を選んで実行します。起動時・定期確認時の自動ダウンロードはありません。

前回の結果は端末ごとの `状況/端末ID/PDF取得結果.json`、実行ごとの履歴は `PDF取得履歴/実行ID.json` に残します。結果の画面表示はこのMacの前回分です。論文ファイル・工程記録はOneDrive経由で他の端末にも共有されます。iPhone用の既存サイトには従来どおり工程件数だけを共有します。

## Batch APIでJSONを作成・回収する（段階4）

1. アプリを再起動し、工程2の **「APIでJSON作成・回収」** を開きます。API操作は担当Mac 1台に限定します。手動取り込みやPDF取得は他のMacでも続けられます。
2. 担当Macのリポジトリ直下の `.env` に `OPENAI_API_KEY=...` を設定します（既存のキーを利用可能）。環境変数があれば優先し、`.env`からはこのキーだけを読みます。キーをOneDriveへ置いたり、画面やチャットへ貼ったりする必要はありません。
3. **「APIキー・担当Mac・予算の設定」** で購入済み残高、他の処理の使用・予約額、予算期間の終了日と残高有効期限の早い方を入力します。期限はUTC日付の開始時刻です。自動チャージ無効と旧Batch等の未精算分を確認し、保存します。設定は最初の1台だけで行い、OneDrive同期後に他のMacを開いてください。
4. PDF取得済み・JSON未作成の論文を1〜5本選び、**「選択した論文の見積もりを準備」** を押します。この時点ではPDFを外部送信しません。PMID・論文名・予約見積を確認します。手動PDF/JSONが取り込み待ちに残っていれば、先に整理してください。
5. 送信のチェックを入れ、**「確認した対象をBatchへ送信」** を押します。既存の `gpt-6.1-sol` / medium / high / fulltext-v4 を使い、最大出力は通常32,000、長いガイドライン等は48,000トークンです。1論文につき1 Batchで記録します。
6. 後で同じ担当Macから **「状況確認・JSON回収」** を押します。Batchは24時間枠の非同期処理です。送信後はMacを終了してもAPI側の処理は継続しますが、JSONの回収・OneDriveへの保存・工程更新には担当Macの起動とこの操作が必要です。アプリ再起動後も元の台帳から照合・回収できます。
7. 検証を通ったJSONは `papers/PMID_番号/files/内容ハッシュ/PMID_番号_master.json` へ保存し、**PNG作成待ち** に更新します。テーマ別JSONとWeb用依頼文も準備します。以後のPNG作成・内容確認は手動です。確認したPNGは段階5のボタン、または手動でNotionへ登録します。

料金は残高確認24時間以内、残高期限まで50時間以上、期間$20・1処理版$4までという既存の制限を使います。予約見積は請求額やプロバイダー側の強制上限ではありません。長いPDFは見積画面に「入力確認が必要・予算枠$4」と表示し、送信確認後にPDFをアップロードして入力トークン数を数えます。再見積もりが予算を超える場合や実入力が272Kを超える場合は、生成Batchを作成せず停止します。原本を勝手に分割・切り捨てません。予算で止まった場合は設定を確認し、再度対象を選んで準備してください。

- **二重送信防止**：Batch作成前に送信意図をローカル台帳へ記録します。応答不明時は再送せず、回収操作でBatch一覧と照合します。送信履歴のある同じPDFは新規送信候補から外します。Batch作成前に失敗したと確認できた場合だけ、明示的な再選択で1回再試行できます。未確定費用は予約を保持します。
- **手動ルートとの合流**：API待ちの間にも手動JSONを保存できます。回収時に手動JSON、PDF差し替え、新しい記録、未整理の手動入力があれば、API結果は `API_JSON/results/処理版ID/` に保管し、現在の工程を変更しません。内容・原本を照合したうえで採用する場合は、取り込み待ちへコピーして整理します。
- **検証失敗**：Schema、PMID、原本ハッシュ、既知の論文名、出力完了状態を検証します。形式は正しくても章参照・推奨割り当て等に不整合があるJSONは、OneDriveにも保存して「生成済み・構造確認待ち」にします。手動修正で先へ進めます。未完了、対応不一致、不正形式、結果欠落・重複は自動採用せず、元の応答を担当Macの台帳に残します。自動再生成はしません。
- **担当Macの記録**：APIキーとSQLiteジョブ・予算台帳はGit管理外のローカル `.env` / `output/json_batch/共通フォルダ識別子/`、共有進捗はOneDriveの `API_JSON/status.json`、担当は `API_JSON/owner.json` に保存します。論文工程の正本は従来の `papers/.../records` のままです。ジョブ台帳は旧 `.paper_pipeline` と分離し、旧ジョブを勝手に回収・再送しません。旧ジョブの費用は今回の残高設定へ反映してください。
- **台帳の保管**：`output/json_batch`、`output/manual_settings.json` はアプリ終了中にローカルでバックアップしてください。台帳や担当設定を削除してもAPI側のジョブは取り消せません。担当設定の同期競合・元台帳の欠落・別Macからの操作は停止します。担当変更や移設は元の台帳を保全してから別途行います。OneDriveは分散ロックではないため、未同期の複数Macで同時に初期設定しないでください。

公式仕様・単価は2026-11-13に [Batch API](https://developers.openai.com/api/docs/guides/batch) と [Pricing](https://developers.openai.com/api/docs/pricing) を確認しました。実装では既存のBatch単価（入力$1・出力$5／100万トークン、キャッシュ等は別計算）を維持しています。

## PNGを確認してNotionへ登録する（段階5）

1. アプリを再起動し、手動作成した全テーマのPNGをOneDriveへ保存して取り込みます。工程が **「PNG確認・登録待ち」** になった論文が対象です。
2. 工程4または論文一覧の **「PNG確認・Notion登録」** を押し、1〜5本を選んで **「選択した論文の登録内容を確認」** を押します。Notionの登録先・既存ページを読み取り、PNGのプレビューを表示します。まだアップロードはしません。
3. 各PNGを原文・JSONと照合し、画像ごとの確認欄にチェックします。必要なら **「PNGを原寸で開く」** で確認します。確認者・確認内容を入力し、表示された登録先への登録確認にチェックします。
4. **「確認した論文をNotionへ登録・再開」** を押します。既存ページが一意に見つかればそこへ追加し、なければ1論文につき1ページを作成します。ページ内にテーマごとの領域を設け、本文・テーマJSON・Master JSON・PNGを保存します。PDF原本はOneDriveに保持します。
5. 全テーマの登録と添付を再取得して確認した論文だけ、OneDriveの工程を **「登録完了」** に更新します。確認者・確認内容・ファイルの版・登録ページを記録し、結果欄からNotionを開けます。画像や記録が途中で変わった場合は「Notion登録済み・工程未反映」とし、新しい版を勝手に完了扱いにしません。

接続には担当Macの `.env` にある `NOTION_TOKEN`・`NOTION_DATABASE_ID` を使います。環境変数があれば優先します。複数データソースがある場合は `NOTION_DATA_SOURCE_ID` も必要です。既存の設定をそのまま使えます。登録先をNotion接続に共有し、読み取り・挿入・更新を許可してください。`PMID` と `Automation ID` はrich_text型（Notionのテキスト型）が必要です。DB構造や権限をアプリが変更することはありません。

最初に登録内容を確認したMacをNotion担当にします。JSON Batchの担当とは独立しており、OpenAIキー・予算設定は不要です。初回設定は1台で行い、OneDriveの同期が終わってから他のMacを開いてください。担当Mac以外でもファイル閲覧・手動作業は継続できます。

- **重複防止**：Automation ID・PMID・正規化したDOI・記録済みページIDを照合します。候補が複数、識別が矛盾、アーカイブ・移動・ゴミ箱の記録がある場合は、新規作成せず停止します。識別項目のない手動ページは照合できないため、登録前にPMIDまたはDOIを記入してください。既存のAutomation IDも照合後に引き継ぎます。
- **中断時**：同じ論文を選び直し、PNGと登録内容を再確認して同じボタンで再開します。作成・追記・添付の前に送信意図を保存し、応答が失われてもページ・領域・添付を照合します。未確定の結果が見つからない場合は、再送して重複させず確認待ちにします。結果不明の旧版を放置して新しい版からページを作成することも止めます。
- **既存内容と確認**：既存の本文・臨床項目・選択済み画像を上書きせず、この版の領域を追加します。新規ページの `Human Checked` はオフのままです。PNG確認と、精読全体の医学的な確認は区別します。既存ページの `Human Checked` は変更しません。本文や添付が後から変更・削除され、保存結果を確認できない場合は完了にしません。
- **添付上限**：接続先の上限とsingle_partの20MiB上限の小さい方を使い、上限超過は登録前に停止します。PNGを勝手に縮小せず、外部の公開URLへも置きません。2026-11-13の実接続の読み取り確認では上限5MiBでした。
- **保管**：NotionトークンとSQLite登録台帳は担当Mac内の `.env` / `output/notion_sync/共通フォルダ識別子/`、共有の担当設定・結果はOneDriveの `NOTION/owner.json`・`NOTION/status.json` に保存します。キー・SQLiteをOneDriveやGitへ置きません。アプリ終了中にローカル台帳と `output/manual_settings.json` をバックアップしてください。元台帳の欠落・担当の競合・登録先の変更があれば停止します。担当変更や台帳移設は記録を保全してから別途行います。

**APIを使わず手動登録する経路も残しています。** 自分でNotionへアップロードした場合は、これまでどおり「確認・登録の記録」で完了を記録してください。PNG生成APIは接続していません。Mac停止中に新規登録は進まず、実行中は担当Macのアプリを開いたままにします。OneDriveへのクラウド同期完了は別途確認してください。

実装は既存の `paper_pipeline/notion.py` のページ照合・アップロード・送信意図記録・再取得確認を再利用しています。公式仕様は [データソース照会](https://developers.notion.com/reference/query-a-data-source)、[ファイルアップロード](https://developers.notion.com/reference/create-file)、[リクエスト制限](https://developers.notion.com/reference/request-limits) を参照しています。

## 保存場所

```text
PubMed_GraRec/
  workspace.json
  00_取り込み待ち/
    希望PMID.txt
    PMID_番号/                PDF・JSON・PNG・メモをまとめて投入
  01_取り込み済み/
    取り込みID/               成功した入力を元の相対パスで保管
  papers/
    PMID_番号/
      受け渡し/
        PDF/                  入手したPDFを保存
        JSON/                 Webで作成したmaster.jsonを保存
        PNG/                  テーマID.pngを保存
      files/内容ハッシュ/     取り込み済みの実ファイル・依頼文（版ごとに保持）
      records/記録ID.json      工程・採用ファイル・端末・時刻・作業メモの履歴
  API_JSON/
    owner.json                API担当Macの識別（キーは含まない）
    status.json               API進捗・見積・費用予約と回収先
    results/処理版ID/         回収JSONの保管コピー・手動変更時の候補
  NOTION/
    owner.json                Notion担当Macの識別（トークンは含まない）
    status.json               選択・確認対象と論文／テーマごとの登録結果
  状況/
    端末ID/
      状況.txt                最終状況とファイルの場所
      状況.html               ローカルブラウザー向けの閲覧用一覧
      snapshot.json           同じ状況のデータ
      取り込み結果.json       この端末の前回の整理結果・残した理由
      PDF取得結果.json        この端末の前回のPDF取得結果
      PDF取得履歴/実行ID.json  PDF取得の実行別結果
```

`files/`・`records/`は編集せず、変更するファイルを`受け渡し/`へ保存します。PDFやJSONの新しい候補を同時に複数置いた場合は、自動で選ばず要確認にします。採用する候補1つを残し、他は共有フォルダ外の作業用フォルダへ移してください。取り込み済みの入力ファイルは自動削除しません。

共有側ではSQLiteもMac内のシンボリックリンクも使いません。各更新は固有名のファイルに追記します。同じPMIDを自宅と職場で並行更新すると、両方の版を残し「要確認・競合」に表示します。時刻だけで片方を上書きしません。両方のファイル・メモを確認し、採用する記録を明示して解決できます。

## iPhone・iPad、Macが停止中の場合

OneDriveの `papers/PMID_番号/files/` からPDF・JSON・PNG・依頼文を開き、Webでの作業に利用します。生成したファイルは `00_取り込み待ち/PMID_番号/` へ保存し、次にMacで「取り込み・整理」を実行します。既存の `受け渡し/JSON` または `受け渡し/PNG` に保存した場合は、Macアプリの次の確認で取り込みます。
進捗は `状況/端末ID/状況.txt` で確認できます。複数端末のファイルがある場合は本文の端末名・記録日時を確認します。HTMLのプレビューやリンク操作は端末・アプリに依存するため、iOSではTXTと実ファイルを基本にします。

**MacBook Airの常時起動は不要です。ただしMacを閉じる前にOneDriveへの同期が終わっている必要があります。**
自宅Macが停止中でも、職場Macのアプリが記録できます。両方のMacが停止中にiPhone/iPadで保存したファイルはOneDriveで共有されますが、共通取り込み待ちの工程記録は次にどちらかのMacで「取り込み・整理」を実行したときに更新します。整理前でも、アップロード済みの実ファイルは閲覧できます。

表示するのは「各Macが最後に記録した状態」であり、クラウド同期完了の保証ではありません。

### iPhoneで状況画面を見る

今までと同じ [PubMed 進捗](https://pubmed-progress-thama.fairkayak3.chatgpt.site) を開き、同じChatGPTアカウントでサインインします。現在のMacアプリと同じ6区分の件数・確認端末・最終確認時刻を表示します。サイトの旧ラベル「手動登録完了」には、今回のNotionボタンから登録した完了分も含まれます。

状況共有を設定したMacでアプリを開いている間、約30秒ごとに件数を共有し、iPhone側も約30秒ごとに読み直します。「いま更新する」でも再取得できます。論文別受け渡しのファイル確認から表示までは通常約1分が目安です。共通取り込み待ちのファイルは「取り込み・整理」の実行後に反映します。`.command` 単独実行でも、状況共有が設定済みのMacでは整理後に件数を1回共有します。未設定・共有失敗でもOneDriveの状況ファイルは保存します。Mac終了・スリープ・通信切断中は最後に共有した状況を表示し、2分以上更新がなければ案内を出します。

共有するのは件数・端末名・確認時刻だけです。論文本文・PMID・ファイル・メモはサイトへ送りません。共有用の認証設定は各Mac内のGit管理外 `.remote_status/config.json` を使い、OneDriveへ置きません。このMacの既存設定を継続利用します。他のMacでも直接共有するには、そのMacにも専用の認証設定が必要です。未設定の場合はMac画面に「状況共有が未設定」と表示します。

JSONの自動回収・旧Push通知は再開しません。

Macで共有フォルダを「このデバイス上で常に保持」に設定すると、作業ファイルをオフラインでも使えます。[Microsoftの説明](https://support.microsoft.com/en-us/onedrive/save-disk-space-with-onedrive-files-on-demand-for-mac)
iOSの「ファイル」アプリにもOneDriveを追加できます。[Appleの説明](https://support.apple.com/en-us/102238)

## 共通の保存・工程更新

段階5の確認後Notion登録まで接続済みです。`intake.organize`、`pdf_download.download_selected`、`json_batch.collect` は同じ `Workspace.import_file` を使い、共通の検証・履歴・工程へ合流します。`json_batch` は既存 `batches.Batches` の送信・回収・予算予約・不明送信の照合を再利用し、画像・Notionの処理へは進みません。Notionは `notion_sync` の選択・PNG確認・登録操作だけで実行し、全テーマの登録確認後に共通Workspaceへ完了記録を追加します。
